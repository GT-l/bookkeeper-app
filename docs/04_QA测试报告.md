## 二、发现的问题（按严重程度排序）

### 🔴 F-01【P0 阻断】银行短信正文含时间即抛异常，短信识别整体失效

- **文件/行号**：`app/src/main/java/com/azu/bookkeeper/automation/receiver/SmsCaptureParser.kt:72-78`、`83-98`
- **问题描述**：`extractTime()` 按 `match.groupValues.size` 分派，但 `groupValues[0]` 是完整匹配：
  - 规则1 `(20\d{2})[-/年]...(\d{2})` 有 **5 个捕获组 → size=6**，落入 `else -> null`，**永远解析不到完整日期时间**；
  - 规则2 `(\d{1,2})月...(\d{2})` 有 **4 组 → size=5**，却调用 `parseFiveGroupTime`，其内部 `g.drop(1)` 只剩 4 个元素，5 元解构 `val (year,month,day,hour,minute)` 调用 `component5()` → **IndexOutOfBoundsException**；
  - 规则3 日期 3 组 → size=4，调用 `parseFourGroupTime`，4 元解构只有 3 个元素 → 同样崩溃。
- **实际影响**：任何带时间戳的银行扣款短信（真实短信几乎都带）在 `parser.parse()` 抛异常；`SmsBroadcastReceiver.kt:93-95` 捕获 Throwable 后仅打日志，不建 CaptureEvent、**不提示用户** → AC-11「抖音短信识别」、AC-16「三路去重」实际不可用，且违反 PRD「不静默失败」。
- **严重程度**：P0（核心增量功能完全不可用 + 静默失败）
- **修复建议**：改为按捕获组数量正确分派：
  ```kotlin
  when (match.groupValues.size) {
      6 -> parseFiveGroupTime(match.groupValues)   // 完整日期+时分
      5 -> parseFourGroupTime(match.groupValues)   // 月日+时分
      4 -> parseDateOnlyTime(match.groupValues)    // 仅日期，补当天 00:00
  }
  ```
  并新增 `parseDateOnlyTime`，或将解构改为按索引取值 + `getOrNull` 保护。相关回归用例：`SmsCaptureParserTest.BUG复现 完整日期时间应从正文提取`、`BUG复现 中文月日时间应从正文提取`。

### 🔴 F-02【P1 严重】分类辅助词 categoryId=0 却优先命中，自动账单无分类且满分入账

- **文件/行号**：
  - `automation/classify/SeedRuleInitializer.kt:78-86`（完成态词 priority=90、字段词 priority=80，均 `categoryId=0L`）
  - `automation/classify/ClassificationRuleEngine.kt:48-56`（`hit != null` 即 `matched=true`，忽略 `categoryId`）
  - `automation/ocr/ConfidenceCalculator.kt:33`（只看 `ruleHit.matched`，不看 categoryId 是否有效）
  - `automation/capture/CaptureCoordinator.kt:150-155`（绕过 `AddBillUseCase.validate`，直接写库）
- **问题描述**：典型支付通知/读屏文本必含「支付成功」「商户名称：」等辅助词，其优先级（80~90）远高于真实商家词（星巴克 30、超市 20）。引擎按 priority DESC 取首个命中，返回 `RuleHit(categoryId=0, matched=true)` → 分类因子拿满 0.15，文本源其余因子也满 → **score=1.0 ≥ 0.75 自动入账，categoryId=0，不弹窗**。
- **数字推演**：文本「支付成功，商户名称：星巴克，金额¥30.00」→ `hit=支付成功(90, catId=0)` → score=`0.30+0.25+0.15+0.10+0.15+0.05=1.00` → 直接建一条**无分类**账单。而 `AddBillUseCase.validate()` 明确规定 `categoryId<=0` 应报 `E_VALID_007`，但自动路径/校对路径均未调用它（仅 `QuickCaptureUseCase` 调用了）。
- **违反**：PRD 22.10「分类/账户未命中 → 归入其他支出并降低置信度，弹窗校对」；AC-1、AC-12、AC-18。
- **严重程度**：P1（账目数据质量污染，用户无感知）
- **修复建议**（两处都应改）：
  1. `ClassificationRuleEngine.classify`：`matched = hit != null && hit.categoryId > 0L`；或过滤掉 `categoryId<=0` 的辅助词不参与分类命中，仅作为完成态信号。
  2. `CaptureCoordinator.buildBill` / `VerificationController.submitDecision`：categoryId<=0 时落到默认「其他支出」分类并强制 `needsVerification=true`；或统一复用 `AddBillUseCase.validate()` 校验。
  3. `ConfidenceCalculator`：分类因子改为 `if (ruleHit.matched && ruleHit.categoryId > 0L) 1f else 0f`。
- **回归用例**：`ClassificationEngineTest.BUG复现 完成态辅助词不应抢占真实分类`、`BUG复现 categoryId为零不应算作分类命中`；`ConfidenceCalculatorTest.BUG复现 辅助规则命中但无分类时不应拿满分类因子`。

### 🔴 F-03【P1 严重】非短信源去重仅内存，跨进程/跨秒后双路重复建单

- **文件/行号**：`automation/dedup/DuplicateDetector.kt:37-48`、`56-73`；`automation/capture/CaptureCoordinator.kt:136-141`
- **问题描述**：`isDuplicateWithTolerance()` 对非短信源（`toleranceSec=0`）在内存去重命中失败后**直接 return false**，从不调用 `billRepository.findDuplicate()` 做库级精确回查。内存 `seen` 集合随进程消亡清空、超过 2000 键会淘汰。
- **数字推演**：读屏在 `12:00:00.900`、通知在 `12:00:01.100` 捕获同一笔 ¥30（秒级键分别为 `12:00:00` 与 `12:00:01`）→ 内存键不同 → 两次都判非重复 → 生成两条账单；若两次捕获之间 App 进程重启，秒级相同也会重复。
- **违反**：AC-6「读屏与通知同时捕获同一笔付款仅生成一条账单」；PRD 22.9 去重规则。
- **严重程度**：P1（核心差异化承诺失效，产生脏数据）
- **修复建议**：在 `isDuplicateWithTolerance()` 内存未命中后，无条件调用 `billRepository.findDuplicate(toDedupKey(candidate))` 做一次库级秒级键回查（短信源再叠加 ±窗口）；或对读屏/通知源也启用一个小容差（如 ±5s）库查。
- **回归用例**：`DuplicateDetectorTest` 中已有精确键/容差键用例；建议工程师修复后补一条「跨实例/跨秒库级回查」用例。

### 🟠 F-04【P2 中】短信已识别的账户被丢弃，多卡用户记错账户

- **文件/行号**：`automation/capture/CaptureCoordinator.kt:166-174`（`fieldsFromSmsSummary` 只读 amount/merchant/billTime，未读 `summary.acct`）
- **问题描述**：`SmsCaptureParser` 已按银行简称+卡尾精配出 `ParsedSms.accountId`，`SmsSummary.acct` 也写入了 CaptureEvent.rawText；但协调层重构 `ExtractedFields` 时 `accountHint=""`，`AccountMatcher.match("sms:ICBC", ...)` 仅按 `DEBIT_CARD` 取第一个启用账户。
- **影响**：用户有多张储蓄卡时，B 卡扣款短信被记到 A 卡，余额错误。
- **修复建议**：`fieldsFromSmsSummary` 解析 `summary.acct`，若 >0 则直接作为 `ruleHit.accountId` 使用（或作为 accountHint 传入 matcher）。

### 🟠 F-05【P2 中】CSV 的 TSV 自动分隔检测恒失效

- **文件/行号**：`data/local/file/CsvDataSource.kt:98`、`147-151`
- **问题描述**：判断条件 `record.size > 1` 要求「按逗号解析后已有多列」，但 TSV 首行按逗号解析只有 1 列（整行是一个含 `\t` 的字段）→ 条件永远 false → delimiter 保持 `,`，制表符文件被当成单列。
- **修复建议**：改为统计原始首行中 `\t` 与 `,` 的出现次数比较（在 `nextRecord` 之前 peek 首行原始字符串），不要依赖已按逗号切分的结果。

### 🟠 F-06【P2 中】CSV 预览未剥离 UTF-8 BOM，自动表头映射失败

- **文件/行号**：`data/local/file/CsvDataSource.kt:95-103`（`readPreview`）对比 `128-152`（`forEachRow` 有 `removePrefix("\uFEFF")`）
- **问题描述**：`detectCharset` 识别 BOM 返回 UTF-8，但 `readPreview` 把带 BOM 的首列表头（如 `\uFEFF交易时间`）原样返回；`FieldMapping.indexFor` 用 `equals` 匹配「交易时间」→ 失败，用户必须手动改映射。
- **修复建议**：在 `readPreview` 读取首行后与 `forEachRow` 同样剥 BOM；或直接让 `Charset.forName("UTF-8")` 的解码器带 BOM 处理。

### 🟠 F-07【P2 中】导入去重键的备注未归一化，与写库键漂移

- **文件/行号**：`domain/usecase/import/PreviewImportUseCase.kt:115-121` 对比 `domain/model/Bill.kt:39-45`、`core/Extensions.kt:20`
- **问题描述**：预览层直接 `DedupKey(remark = remark)`（仅 trim），而 `Bill.dedupKey()` 走 `normalizeRemark()`（折叠连续空白）。源文件里「超市  购物」与库内「超市 购物」键不同 → 库内去重漏判；同一批两行空白差异也会被当成不同账单。
- **修复建议**：`PreviewImportUseCase` 构造 DedupKey 时使用 `remark.normalizeRemark()`。
- **回归用例**：`ImportCleaningTest.BUG复现 导入去重键与账单去重键备注归一化应一致`。

### 🟠 F-08【P2 中】用户介入分支把事件置成 CONSUMED_AUTO，违反终态契约

- **文件/行号**：`automation/verify/VerificationController.kt:181-191`
- **问题描述**：低置信度弹窗用户确认后，若二次去重命中，`captureDao.markStatus(decision.eventId, CONSUMED_AUTO.code)`。该路径是用户介入路径，按主理人裁决应为 `USER_CORRECTED`；且未建账单却置「自动入账完成」语义错误。
- **修复建议**：改为 `USER_CORRECTED`（或直接 `DISCARDED` 并在文案中说明「已存在相同账单，本条丢弃」）。

### 🟠 F-09【P2 中】DISCARDED 事件误阻断手动补记

- **文件/行号**：`data/repository/BillRepositoryImpl.kt:136-141`（`event == null || status.isTerminal` 均视为已处理）+ `domain/usecase/quick/QuickCaptureUseCase.kt:39-46`
- **问题描述**：`DISCARDED` 是终态，因此被丢弃或被自动去重掉的事件，用户想通过「一键补记」手动录入时，`isAlreadyHandled` 返回 true，表单被短路并提示「该笔已补记，无需重复添加」（与事实不符）。
- **修复建议**：`isCaptureEventHandled` 只把 `CONSUMED_AUTO` / `USER_CORRECTED` 视为已补记；`DISCARDED` 允许重新走快捷补记（补记成功时 `markStatus` 会把它置 `USER_CORRECTED`）。

### 🟠 F-10【P2 中】带标签的时间行解析失败，回落到达时间

- **文件/行号**：`automation/ocr/FieldExtractor.kt:36-39`
- **问题描述**：`extractTime` 对整行调用 `parseFlexible`，而通知/读屏常见文本是「交易时间：2026-11-22 12:30:45」，整行带前缀导致所有 pattern 失败 → 回落 `fallbackTime`（到达时间）→ 时间因子由 1.0 降为 0.5（`ConfidenceCalculator` 若 timeSource=SMS_ARRIVAL）或去重键按到达秒计算。
- **修复建议**：从行中提取首个符合日期时间模式的子串再解析（正则 `20\d{2}[-/年]...` 或 `DateTimeUtils.parseFlexible` 增加「前缀剥离」分支）。
- **回归用例**：`FieldExtractorTest.BUG复现 带标签的时间行应可解析`。

### 🟠 F-11【P2 中】短信金额正则取首个匹配，可能误取「余额」

- **文件/行号**：`automation/receiver/BankSmsRule.kt:66`、`SmsCaptureParser.kt:59-67`
- **问题描述**：`amountRegex` 取正文中第一个两位小数数字。短信若写成「当前余额8888.88元，本次支出1234.56元」，会把余额当金额建单。
- **修复建议**：优先匹配「支出/扣款/消费/交易金额」标签后的数字；无标签时排除「余额/可用额度」之后的数字。

### 🟡 F-12【P3 低】XLSX 读取非真正流式

- **文件/行号**：`data/local/file/XlsxDataSource.kt:56`、`115`
- **问题描述**：读取用 `XSSFWorkbook(OPCPackage.open(...))`，整表对象模型入内存（虽有 10MB 上限）。注释称「流式读取」不完全准确；万行级 xlsx 内存占用偏高。
- **修复建议**：改用 `XSSFReader` + SAX `XSSFSheetXMLHandler` 真流式读取。

### 🟡 F-13【P3 低】短信权限未走运行时申请，且 RECEIVE_SMS 从未校验

- **文件/行号**：`automation/permission/PermissionGuide.kt:51-53`、`ui/settings/AutomationSettingsViewModel.kt:134-142`、`AndroidManifest.xml`（receiver 的 `android:permission="android.permission.RECEIVE_SMS"`）
- **问题描述**：`hasSmsPermission()` 只查 READ_SMS；设置页「去授权」跳应用详情页（非运行时弹窗）；Manifest 同时声明 READ_SMS/RECEIVE_SMS，但代码从不校验 RECEIVE_SMS。
- **修复建议**：按 PRD 23.3.2 用 `ActivityResultContracts.RequestPermission` 运行时申请 READ_SMS（含前置用途说明卡片），并同时校验/申请 RECEIVE_SMS 或在 Manifest 去掉 receiver 的 permission 限制。

8. 关闭短信开关/撤销权限 → 功能降级不崩溃，其他源正常（AC-17）。
9. 断网飞行模式跑完整识别流程（AC-9）。
10. 性能：单笔捕获→识别→入计时（AC-10，目标 <2s）。

4. 导入 500/501/1000 条 → 确认每 500 条一个事务、进度回调次数正确。

### 6.5 余额一致性手工回归（用 UI 核对数字）
1. 现金账户初始 ¥100 → 记支出 ¥30 → 余额 ¥70。
2. 编辑为 ¥50 → 余额 ¥50（再扣 ¥20）。
3. 编辑换账户（现金→微信）→ 现金恢复 ¥100，微信 -¥50。
4. 转账 ¥20 现金→微信 → 现金 ¥80、微信 +¥20。
5. 删除该转账 → 两边回滚。
6. 信用卡初始 0 → 支出 ¥100 → 余额 -¥100（欠款 ¥100）；还款转账 ¥100 → 余额 0。
7. 余额校准输入 ¥88.88 → 生成 ADJUSTMENT 账单，余额更新但统计/预算不变。
