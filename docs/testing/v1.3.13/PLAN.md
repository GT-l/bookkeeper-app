# 识屏完全无响应 —— 技术方案（v1.3.13）

> 这份文档先讲清楚「为什么」，再讲「改什么」。上一版直接改识别逻辑属于结论先行，是本轮要纠正的。

---

## 一、现象拆解

用户反馈两句话，指向完全不同的层：

1. **「微信所有界面都触发不了自动识屏」** —— 表面看像识别规则问题；
2. **「log 日志都不触发」** —— 这一句改变了判断：如果连入口日志都没有，说明代码根本没被执行到，问题在**事件投递**，不在识别。

3. **「更新之后无障碍识屏也被关闭了」** —— 独立问题，属于系统授权生命周期。

关键证据（用户上一条诊断日志）：

```
ERROR[A11Y] 无障碍异常 kind=closed enabled=false wasEnabled=true
  source=com.android.packageinstaller api=37 revokeCount=5 pidStable=false
```

`source=com.android.packageinstaller` + `revokeCount=5` = **每次覆盖安装 APK，Android 都会撤销无障碍授权**。这是系统安全设计，不是 App 的 bug。

---

## 二、三层排查模型

「微信里没反应」只有三种可能，必须按层排除，不能跳步改识别规则：

```
第 1 层：系统有没有把事件投给服务？
        ├─ 没有 → 服务没绑定 / 开关被关 / ROM 限制   ← 本机最可能
        └─ 有 ↓
第 2 层：事件有没有通过包名与页面过滤？
        ├─ 没有 → 包名白名单 / 类名错误              ← 之前 v1.3.8 就踩过
        └─ 有 ↓
第 3 层：字段抽取有没有拿到金额与商户？
        └─ 拿到就记账，拿不到才看规则
```

**本轮先在第 1 层加"仪表"**，而不是继续在第 3 层调规则。

---

## 三、改动清单

### 3.1 新增「无障碍事件到达」自证（核心）

`AccessibilityEventStats`：
- 在 `dispatchEvent` 的**第一行**计数（任何过滤之前）
- 记录：今日事件总数、其中支付应用条数、最后一条时间 / 包名 / 事件类型
- 按天重置，落盘节流 5 秒，不影响主线程

自检页新增一行：

| 读数 | 结论 | 下一步 |
| --- | --- | --- |
| 今天 0 条 | 系统没投递事件 | 服务实际未绑定 → 重开无障碍；不是识别规则问题 |
| 有事件，支付应用 0 条 | 包名被过滤 | 查 `PAYMENT_PACKAGES` / `event.packageName` |
| 有事件，支付应用 > 0 | 事件正常 | 查页面识别与字段抽取 |

这一项把"猜"变成"读数"，后续任何反馈都能 5 秒定位层级。

### 3.2 识屏日志默认开启

`CaptureLog` 原默认 `false`，导致用户出问题时日志文件几乎为空（只有 `force` 级别的连接/解绑记录）。
改为默认开启：只存本机、上限 256KB 自滚动。用户可在设置关闭。

### 3.3 回到前台即体检无障碍

`MainActivity.onResume` → `A11yWatchdogService.checkNow()`：
- 有 `WRITE_SECURE_SETTINGS`（曾跑过 ADB restore）→ 立即写回授权；
- 没有 → 发一条「识屏被关闭」通知。

以前只有「自动记账前台服务在跑」时才会被守护发现；没开自动化的用户即使安装后被撤销，也看不到任何提示。

### 3.4 存储排查补两类残留

| 类别 | 位置 | 说明 |
| --- | --- | --- |
| 安装包残留 | `files/updates/*.apk`、`cache/incoming-apk/*.apk`、`cache/*.apk` | 每个约 90MB，安装后本应自动删 |
| 日志与诊断 | `files/capture_log.txt` 等 | 单独标注「自检页复制 log 的来源」 |

两者都可勾选删除，删除前有二次确认；数据库与密钥仍然锁定。

## 四、为什么"更新后无障碍被关闭"

### 事实

- Android 在**应用被覆盖安装（package changed）后会撤销无障碍授权**，这是 AOSP 行为，任何 App 都无法阻止；
- realme / ColorOS 系额外有「长时间未使用自动关闭无障碍」的策略；
- 用户日志 `revokeCount=5` 与 `source=com.android.packageinstaller` 完全对得上。

### 能做的三件事

| 方案 | 代价 | 效果 |
| --- | --- | --- |
| A. 每次安装后手动重开 | 一次点击 | 立即恢复 |
| B. ADB 授权 `WRITE_SECURE_SETTINGS` 一次 | 电脑执行一次脚本 | 之后**自动恢复**，无需再手动 |
| C. Shizuku / Shevery 锁定服务 | 装一个工具 | 最稳，不受厂商策略影响 |

App 侧已具备 B 的能力（`AccessibilityHealth.tryRestore`），本轮把它提前到「每次回到前台」，不再依赖自动记账服务是否在跑。

## 五、如果事件计数为 0 的后续处置

按顺序执行，每一步都能独立验证：

1. 设置 → 无障碍 → 少花点儿：关掉再打开（重新绑定服务，同时让 `canTakeScreenshot` 能力按新 XML 注册）
2. 回到 App → 自检页看「无障碍事件到达」是否开始增长
3. 仍为 0：
   - 检查 realme「应用自启动 / 后台限制 / 省电优化」是否限制了本应用
   - 检查是否开启了「无障碍快捷方式」之外的隐私保护（部分 ROM 的「隐私空间」会隔离无障碍）
4. 跑一次 `scripts/android_unlock_accessibility.sh restore`（ADB），之后安装不再掉授权

---

## 六、本版不改什么（避免再次误伤）

- **不改任何识别规则、词表、置信度**：在"事件有没有到"没确认之前，改规则等于盲改。
- 不新增第二个无障碍服务（会多一个系统授权项，体验更差）。
- 不动 `canTakeScreenshot`：如果后续证实该能力导致 realme 拒绑，再单独做「兼容模式」并让用户选择。

---

## 七、验收标准

1. 自检页稳定显示「无障碍事件到达：今天 N 条（支付应用 M 条）· 最后一条 …」；
2. 在微信里滑动、切页时 N 与 M 持续增长；
3. 关闭无障碍开关后，MainActivity 回到前台 1 秒内出现通知提醒；
4. 存储排查能列出 `updates/*.apk` 与 `capture_log.txt`，且能删除前者。
