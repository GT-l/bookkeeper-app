# v1.3.18 节点采集判据：从「文本稀疏」改成「交易证据」

## 一、问题

微信这类自绘 / WebView 页面，根节点往往能返回**几行无关文本**（返回 / 支付 / 完成）。
旧逻辑用 `ScreenTextCollector.isSparse`（行数 < 3 或长度 < 8）判断「文本够不够」：

- 文本不稀疏 → 不再读事件来源、不再读其它窗口 → 金额在别处永远读不到；
- 文本不稀疏 → 也不触发截图 OCR 兜底 → 连最后的补救都没有。

结果就是用户看到的「打开了付款记录，什么都不发生」。

## 二、修改

| 位置 | 修改 |
| --- | --- |
| `PaymentScreenRecognizer` | 新增 `hasTransactionSignal(text)`：`¥/￥`、金额行、`RECEIPT_CONTEXT`（交易单号/账单详情/支付时间…）任一命中即为「有证据」 |
| `PaymentAccessibilityService.readScreenText` | 停止条件改成「没有交易证据」→ 继续读 `event.source` + 最多 3 个窗口，读到证据立刻停 |
| `PaymentAccessibilityService.readScreenSnapshot` | 摇一摇入口用同一判据，避免两条链路采集口径不同、结果漂移 |
| `dispatchEvent` UNKNOWN 分支 | 截图 OCR 触发条件补上「无交易证据 + 页面像交易页」；页面词表 `PAGE_HINTS` 仅用于触发，不参与记账 |
| 节流 | 仍受 15 秒 `SHOT_FALLBACK_INTERVAL_MS` 保护，不影响耗电 |

## 三、对静态检查报告的取舍

| 报告项 | 结论 | 理由 |
| --- | --- | --- |
| 多窗口读取被稀疏条件挡住 | **采纳** | 已按交易证据判据重写，两条链路统一 |
| 截图 OCR 只看稀疏 | **采纳** | 补「有文本无证据 + 像交易页」条件 |
| 无障碍节点读取在 IO 线程 | **不采纳** | `AccessibilityNodeInfo` 是 Binder 快照，后台线程读取是安全的；搬到主线程反而增加卡顿与 ANR 风险 |
| 强制识屏未先判页面类型 | **暂缓** | 现有链路里「有金额但场景未知」多为有效凭据页，先判类型会把这类页面直接丢掉 |
| 关键词覆盖不全（付款记录等） | **暂缓** | 上一轮盲改词表造成过误判；先修采集，再看是否仍缺 |
| 弱详情词要求金额行 1–3 | **不改** | 这是防止「把账单列表当成一笔」的闸门，改动会重新引入整列表被记成一笔 |
| 事件类型偏少 | **不改** | 增加 `typeViewTextChanged/Scrolled` 会显著放大事件量，且不解决自绘页面问题 |
| 截图有效性只靠单色帧 | **部分改善** | v1.3.16 已改为「亮暗跨度」判单色；内容是否含交易区域仍靠 OCR + 交易证据判定 |

## 四、用例

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| P-01 | 微信付款记录（根节点几行标题） | 继续读其它窗口；仍无金额则退截图 OCR（15s 节流） |
| P-02 | 微信聊天页（有「转账」字样） | 最多触发一次 OCR，识别不出场景不提交 |
| P-03 | 支付宝扣款成功页 | 根节点有金额 → 不额外读窗口，行为与之前一致 |
| P-04 | 摇一摇在付款记录页 | 与自动识屏读到同样的窗口集合 |
| P-05 | 页面只有「返回/支付/完成」 | `hasTransactionSignal=false`，不再被当成「文本够用」 |
