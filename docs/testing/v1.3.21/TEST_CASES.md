## 跳过原因（工单交付要求 3：日志不足必须明确输出，不猜测规则）

### 二 · 条件 B（纯拼音伪装）—— 跳过原因
工单「判定逻辑」写了条件 B，但「验证样本」四条里**没有任何一条**是纯拼音连续字母
（如 `Aierpu` 这类 ≥6 位无空格字母）的输入。按工单红线
「任何无 原文= 日志支撑的规则，一律不写、不合并、不猜测」，本轮不实现。
风险说明：纯拼音与纯英文（白名单 `AirPods Pro`）在「连续字母」这一特征上重叠，
没有拼音词典就无法区分，强行实现必然误伤白名单，违背「宁可漏记不可错记」。
补样本后可按同一 `GoodsOcrAnomaly` 结构追加 `conditionB()`。

### 三 · 退款生成收入冲正 —— 跳过原因
1. 工单「验证样本」是状态描述（`原订单：支出 100 元，status=success` /
   `退款状态识别到：已退款 100 元`），**不是 OCR 原文行**，不满足红线的日志支撑要求；
2. 现有 `Bill` 模型没有 `status` 字段，写入 `status = "refunded"` 需要数据库迁移，
   本工单明确「无日志不改动」，不做无依据的 schema 变更；
3. 现有 `Refund` 模型只有 `sourceBillId`，没有 `related_order_id` / `note` /
   `category = "退款冲正"` 字段，且 `AddRefundUseCase` 的幂等是「累计不超过原账单金额」，
   不是工单要求的「同一 order_id 仅冲正一次」；
4. 盲写会出现「待支付页被冲正」「同一单多次冲正」，直接违背最高原则。
现有「退款管理」页已支持手动登记退款并自动生成收入账单，路径可用，故本轮不动。

### 四 · 群收款单笔详情 —— 跳过原因
工单「安全策略」原文：「当前无专用群收款词表；通用 DETAIL 规则命中率不保证 → 不强行覆盖；
无完整日志 → 不写规则 → 不修改代码；仅当日志出现锚点 ≥1 时才解析」。
本轮没有收到真实群收款详情页的 OCR 日志，因此不新增词表、不新增解析分支。
工单末尾给出的「日志提交格式要求」是提交模板，不是真实 captured 日志，不作为实现依据。

### 五 · 转账 / 红包 —— 冻结
`PaymentScreenRecognizer.kt` 的 `TRANSFER_IN_HINTS`、`TRANSFER_OUT_HINTS`、
红包判定、`PENDING_TRANSFER` 状态机一字未改。静态脚本 `T-FROZEN-01` 用 SHA-256 钉住：
`6f39f8c5d23d9b19b8ff220eab38bfeadb627dc100a1b741ae2b37edff437eb5`。

## 六.5 自测：非最终页不记账

`NonFinalPageGuardTest` 钉住以下页面判为 `ENTRY` 而非 `SUCCESS`：
- 待支付页（待支付 + ¥金额）
- 选择付款方式页（选择付款方式 / 零钱 / 银行卡 / 确认付款）
- 收银台发起页（向商家付款 / 付款码 / 请输入支付密码）
- 通用断言：`待支付 / 选择付款方式 / 向商家付款 / 确认支付 / 待确认收款` 五个锚点均不判 SUCCESS
