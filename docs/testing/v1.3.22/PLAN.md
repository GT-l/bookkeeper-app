# v1.3.22 技术方案：微信支付场景识别与识屏触发修复

> 工单要求「每个方案需附带可行性评估（技术难度 / 架构影响 / 测试成本）」。
> 本文先给调查结论，再逐方案评估并给出选择。**未接到任何 `原文=` 日志的识别规则，一律不写**（沿用 v1.3.21 红线）。

---

## 零、调查结论（先证据，后方案）

| # | 工单现象 | 源码证据 | 真实根因 |
|---|---|---|---|
| 1 | 微信各场景不触发 | `accessibility_service_config.xml` 只订阅 `typeWindowContentChanged\|typeWindowStateChanged`；`Constants.PAYMENT_PACKAGES` 含 `com.tencent.mm`；上一版真机日志「今天支付应用 1249 条」但无 `[SCREEN] 提交识别` | **事件到了，不是没到**；卡在 `classify()` 判定 / 静默期，而非事件订阅 |
| 2 | 手动识屏字段不全 | `PaymentTextAnalyzer` 走「候选生成 + 打分择优」；无微信订单专用模板；`extractBestGoods` 不处理跨行金额 | 缺真实 OCR 原文无法定位断链点；盲加模板会误伤其它页面 |
| 3 | 同一转账重复记收入 | `SETTLED_QUIET_MS=12s`（抖音 60s）；`differentBillByTime` 在两个页面时间不同时**直接放行**；DB 去重键 = 秒级时间 + 金额 + 备注，备注带「微信收款 · 对方」前缀 | 转账详情页反复扫描、页面时间抖动 → 静默期被绕过；24h `findRecentDuplicate` 只提示不拦截 |
| 4 | 识别到收单机构而非商户 | `MERCHANT_EXCLUDES` 仅含 财付通/银联/支付科技/支付有限，**缺 网联/快钱/易宝/拉卡拉/微信支付**；规则一只处理「财付通」独占行 | 黑名单不全 + 回溯只认财付通 |
| 5 | 几十条数据近 4MB | `CaptureEventEntity.raw_text` 全量落库（上限 6000 字）；`CaptureDao.deleteOlderThan()` **全项目无调用点**；`bills.ocr_raw_text` 已截 2000 字 | 捕获事件表只增不减 + 全文 rawText 长期滞留 |

## 一、问题 1：微信场景无法触发识屏

| 方案 | 技术难度 | 架构影响 | 测试成本 | 评估 |
|---|---|---|---|---|
| A 增加微信触发锚点白名单 | 中 | 中：要改 `classify()` 前置判定，直接触碰冻结的 `PaymentScreenRecognizer` | 高：需每种场景真实原文 | ⏭ 不选。无 `原文=` 样本；且日志证明事件已到达，加锚点不解决判定断链 |
| B 降低阈值「疑似即解析」 | 低 | 高：会让 `ENTRY`（待支付/选择页）被提交，直接违反「待支付页严禁记账」 | 中 | ⏭ 不选。与最高原则冲突，收益不抵风险 |
| C 页面变化监听（MutationObserver / 更多事件类型） | 中 | 中：需扩 `accessibilityEventTypes` 到 `typeViewTextChanged/typeViewScrolled`，事件量放大数倍 | 高 | ⏭ 不选。Android 无 DOM Observer；上一版真机日志已证明事件量充足，扩大监听只增耗电 |
| **D 手动触发 + 标记待完善场景 + 收集日志** | **低** | **低：只改日志/诊断文案，零识别逻辑改动** | **低** | ✅ **选**。把「事件到了但没判定成」的情况显式写进日志，用户可据此补 `原文=`；手动识屏路径保留 |

**选择 D 的落地**：UNKNOWN 分支日志新增「待完善场景」标记 + 原文预览（已有节流），并在诊断页说明「支付应用事件已到达但未命中场景时，请复制 log 提交」。不新增任何触发词表。

---

## 二、问题 2：手动识屏后字段提取不全

| 方案 | 技术难度 | 架构影响 | 测试成本 | 评估 |
|---|---|---|---|---|
| A 微信订单专用解析模板 | 高 | 高：新增独立分支，需大量真实原文 | 高 | ⏭ 不选。工单未给任何 `原文=`，模板只能靠猜 |
| B 邻近搜索 + 字段置信度评分 | 中 | 中：改 `extractBestMerchant/Amount` 打分 | 中 | ⏭ 不选。无样本时调权会误伤已有 418 项静态基线覆盖的场景 |
| C 预处理归一化 | 低 | 低 | 低 | ⏭ 部分已有：`mergeLatinContinuation`、`¥/￥` 兼容、`GOODS_EXCLUDES` 干扰过滤均已在 v1.3.11/v1.3.20 实现；无新样本不再加 |
| **D 调试模式输出中间结果** | **低** | **低：不改判定，只增加可选日志** | **低** | ✅ **选**。开启后输出原始 OCR 文本 / 字段候选 / 最终决策，下一份日志即可定位断链点 |

**选择 D 的落地**：在 `PaymentAnalysis` 增加可选 `trace: String`（默认空），由新增的 `AutomationSettingsDataStore.parseTraceEnabled` 开关控制；分析时把「金额候选 / 商户候选 / 商品候选 / 最终取值」拼成一行写入 `CaptureLog`。**开关默认关**，不影响日常日志体积；不改变任何字段取值。

---

## 三、问题 3：同一转账重复记收入

| 方案 | 技术难度 | 架构影响 | 测试成本 | 评估 |
|---|---|---|---|---|
| **A 唯一标识去重** | **低** | **低：纯函数 + 复用现有 `transactionTimeKey`，不碰冻结词表** | **低** | ✅ **选**。用「页面交易时间 + 方向 + 金额 + 对方」做稳定指纹，页面时间抖动时不再直接放行 |
| B 页面签名缓存（24h 哈希） | 低 | 中：新增本地缓存 + 清理策略，页面微变即失效 | 中 | ⏭ 不选。与 A 重叠，且哈希对排版变化脆弱 |
| C 已处理标记（消息 ID） | 中 | 高：需从 OCR 提取 ID + 新存储字段 | 高 | ⏭ 不选。无 `原文=` 证明微信详情页有可提取 ID |
| D 延迟合并草稿 | 高 | 高：改记账时序与 UI | 高 | ⏭ 不选。改动面过大，且会把「真实两笔同额转账」误合并 |

**选择 A 的落地**：修 `differentBillByTime` 的放行条件——仅当「双方时间 key 都能解析且确实不同」才放行；任一为空时仍受静默期约束。转账/红包收入场景静默期与抖音一致取 60s（已有先例）。补纯函数单测 + 服务层单测。

---

## 四、问题 4：识别到收单机构而非真实商户

| 方案 | 技术难度 | 架构影响 | 测试成本 | 评估 |
|---|---|---|---|---|
| **A 收单机构黑名单并强制排除** | **低** | **低：只改 `PaymentTextAnalyzer.MERCHANT_EXCLUDES`（非冻结文件）** | **低** | ✅ **选**。工单直接点名 财付通/网联/银联/快钱/易宝/拉卡拉，属显式需求，不是猜测 |
| B 加权评分（品牌库） | 高 | 中：需维护品牌库 | 高 | ⏭ 不选。无品牌库样本，权重只能猜 |
| C 位置权重 | 中 | 中：OCR 布局坐标在无障碍节点里不存在 | 高 | ⏭ 不选。当前主链路是节点读屏，没有可靠坐标 |
| **D 上下文追溯强化** | **低** | **低：扩展 v1.3.21 的 `ChannelMerchantResolver`** | **低** | ✅ **选**。把「独占行财付通」扩展到工单点名的其它通道名，回溯窗口内按小程序/店铺/SKU 取真实商户 |
| E 用户反馈修正 | 高 | 高：新增 UI + 训练数据回流 | 高 | ⏭ 不选。无回流通道，本版不做 |

**选择 A+D 的落地**：黑名单补齐工单点名通道；`ChannelMerchantResolver` 支持多通道 token；两者都有单测。不动 `PaymentScreenRecognizer`（SHA-256 继续冻结）。

---

## 五、问题 5：数据库体积过大

| 方案 | 技术难度 | 架构影响 | 测试成本 | 评估 |
|---|---|---|---|---|
| **A 分析膨胀原因 + 清理冗余字段** | **低** | **低：已有 `deleteOlderThan()` 无调用点，接上即可；rawText 加长度上限** | **低** | ✅ **选**。根因明确：事件表只增不减 |
| B 拆表分离大字段 | 高 | 高：需 Room migration（当前 DB version=2） | 高 | ⏭ 不选。几十条数据不需要拆表 |
| C WAL + VACUUM / 压缩扩展 | 中 | 中：SQLCipher 下 VACUUM 需独占连接，易引发并发问题 | 中 | ⏭ 不选。先做 A，实测仍大再评估 |
| D 改紧凑格式 | 高 | 高：金额已是分(INTEGER)、枚举已是 Int，无收益 | 高 | ⏭ 不选。现状已满足 |
| **E 定期归档清理** | **低** | **低：复用 A 的清理入口，按保留天数策略** | **低** | ✅ **选**。终态事件 7 天清理，待校对事件保留 |

**选择 A+E 的落地**：新增 `CaptureEventPruner`（纯策略函数 + UseCase），在 `CaptureCoordinator.onCapture` 里按 24h 节流调用；`capture_events.raw_text` 落库截 2000 字（与账单一致）。补单测断言「待校对不删、终态超期才删、节流生效」。

## 六、回归场景对应

| 工单回归场景 | 本版可达成 | 依据 |
|---|---|---|
| 不同微信支付场景均能触发识屏 | ⚠️ 部分：事件到达已证实；判定断链点需下一份 log | 选择 D（问题1）先让日志自证，不猜规则 |
| 手动识屏字段完整、商户优先真实商户 | ✅ | 问题 4 选择 A+D；问题 2 选择 D 提供中间结果 |
| 同一转账扫描多次只产一条收入 | ✅ | 问题 3 选择 A |
| 1000 条记录不超过 10MB | ✅ | 问题 5 选择 A+E；rawText 2000 字 × 1000 ≈ 2MB 量级 |

---

## 七、明确不改

- `PaymentScreenRecognizer.kt` 的转账/红包词表与状态机（继续 SHA-256 冻结）；
- 任何无 `原文=` 支撑的新识别规则（问题 1-A/B、问题 2-A/B、问题 3-C、问题 4-B/C）；
- 数据库 schema / migration（本版只做数据清理与长度限制）。
