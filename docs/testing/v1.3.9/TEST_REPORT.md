## 二、根因分析

### 1. 「识别到付款但识别不出金额」

微信「账单详情」的金额节点是独立的 **`-23.00`**：没有 `¥`、没有「元」、也没有「金额」标签。
`PaymentTextAnalyzer` 原有三条金额正则：
`AMOUNT_SYMBOL`（要求 ¥/￥）、`AMOUNT_LABELLED`（要求「实付/付款金额…」同标签）、
`AMOUNT_YUAN`（要求「元」后缀）——**一条都命中不到**，于是 `amountFen = null`。

修复：新增 `AMOUNT_BARE`（整行纯数字，允许正负号与货币符号），分值压到最低（3），
任何带标签/符号的候选仍然优先；原有「订单号 / 手机号 / 日期 / 余额优惠」淘汰规则继续生效。

### 2. 商户名变成「财付通支付科技有限公司」

微信账单详情是 **标签一行、值下一行** 的版式：

```
商户全称
星巴克咖啡有限公司
收单机构
财付通支付科技有限公司
```

`extractBestMerchant` 只有「同行标签」一条主路，匹配不到 → 落到后缀兜底，
第一个含「公司 / 科技」的行正好是收单机构，于是商户名成了收单机构。

修复三重：
1. `MERCHANT_BARE_LABELS` + 「取下一行」分支，按标签取值；
2. 纯标签行先排除（否则正则的 `商户` 备选会把「全称」两字当成值）；
3. `MERCHANT_EXCLUDES` 增加 收单机构 / 支付机构 / 财付通 / 银联 / 支付科技 / 支付有限。

识别器侧 `refineWeChatText` 同步收紧：页面上存在「收单机构」字段时，不再猜测商户；
只在有明确商户标签时才补 `商户：` 行。

### 3. 页面切换与上下滑动卡顿

`HomeViewModel.UiState.dayGroups` 原本是 **派生 getter**：

```kotlin
val dayGroups: List<DayGroup>
    get() = bills.take(visibleCount).groupBy { ... }.map { ... }
```

每次访问都会重新 `groupBy` + 两次 `filter` + `sumOf`，产生 1 个 Map + N 个 List + 2N 个过滤 List。
首页一次重组会访问 2~3 次（标题计数、概览卡、列表），账单几百条时开销成倍放大。

修复：改为构造时单次遍历 `buildDayGroups()`，同时预算 `incomeFen` / `expenseFen`；
`copy()` 走主构造器，数据变更仍即时生效。

另外列表行 `SoftCard` 由 3dp elevation 改为 `flat = true`（0dp）：
每行一条 RenderNode 阴影是中低端机滚动掉帧的主要来源，层级改由间距 + 1.5dp 描边表达。

### 4. 关于页更新介绍

由「每个小版本一条」改为「最新版本 + 三条大版本里程碑」（v1.3 系列 / v1.2 系列 / v1.0-v1.1）。

## 三、边界与风险

1. 商户抽取改为「宁可留空也不写错」：无标签页面不会再有兜底猜测出来的商户（除无收单机构字段时仍保留旧兜底）。
2. 整行纯数字金额在极少数版式（如页面只有「88」这样的整数）可能被当成金额，仍受 7 位以上整数、日期、余额优惠等规则约束。
3. 本轮未切换为 release 构建：debug 构建本身比 release 慢是系统性因素，若优化后仍不理想，下一轮再评估换 release 产物（同签名，可覆盖安装）。
4. 真机用例 D139-01 ~ 07 需在设备上执行。
